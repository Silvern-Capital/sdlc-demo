STEP 01the repo2 min

Beacon, and the ticket.

A site-health dashboard: six sites, an API, ten tests, no export. Finance wants a CSV they can open in Excel. That is the ticket.

Do this

Terminal A. Leave the server running there for the whole workshop.

git clone https://github.com/Silvern-Capital/sdlc-demo.git && cd sdlc-demo && npm install && npm run serve

Terminal B. This is where you stay from now on.

cd sdlc-demo && claude
curl -s localhost:8000/api/stores | head -c 400
node --test tests/*.test.js

Open localhost:8000 in your browser. Two tests, green, under a second.

Before you type anything into Claude

Hand Claude the ticket, walk away ten minutes, come back to “done, tests pass”. What could be wrong that nobody notices?

  • A column is missing.
  • A name with a comma splits into two cells.
  • Five rows instead of six.
  • A failing test marked skipped.

Each is easy to catch with a check. None is caught by asking Claude to be careful. This workshop builds the checks.

STEP 02CLAUDE.md3 min

CLAUDE.md asks. It cannot enforce.

Claude reads this file at the start of every session. Every rule in it is a sentence Claude has to remember.

Do this

cat CLAUDE.md
CLAUDE.mdthe whole file, about 30 lines
# Beacon · Site Health

Internal IT-Ops dashboard for the Silvern Capital site fleet. Static page,
no build step. `npm run serve` serves it on :8000 with the API at /api/stores.

## Conventions
- Plain ES5 inside <script>: var and function expressions, no modules.
- Status vocabulary is fixed: "ok" | "warn" | "down".
- window.STORES (from data.js) is the single source of truth. Read it,
  never mutate it.
- Colors come from the :root custom properties in index.html.

## What done means, for any change
- A test in tests/ asserts the new behavior. Write it first; watch it fail.
- Run `node --test tests/*.test.js` after every change; it reports 0 failing.  ← already a hook. You delete this line in step 4.
- `node scripts/lint.js` reports 0 warnings.   ← already a hook. You delete this line in step 4.
- Never edit an existing test to make it pass.   ← stays. Step 3 also puts it in the goal.
- Paste the test and lint output in your final
  message, do not summarize it.

## Workshop mode
This repo is used for a hands-on workshop. Treat every feature request as a
first-time implementation; do not look for, mention, or defer to earlier
branches or pull requests for the same feature.

Then ask Claude

Read CLAUDE.md. Which of these rules could a program check, and which need a person’s judgment?

Expect: tests, lint, “never edit a test” and “paste the output” are checkable. The style rules need a person. A rule a program can check should be a check. Step 4 shows two that already are.

Why the file is short

It sits at the front of the prompt, so it is cached and cheap. What caching does not remove is the space. Every line takes room in the context window on every task, whether it applies or not, and that room is what Claude has left for your code and the test output. So the file holds only what is always true. Checks live elsewhere, where they take no room and cannot be skipped.

Where you put itWhat it takes from the context window
CLAUDE.mdthe whole file, every session, cached but still taking the space
an MCP serverevery tool’s name and schema, every session, used or not. Why this workshop leaves MCP out
a skillone line every session, the body only when used
a subagentone line; its work happens in its own context
a hooknothing, until it finds something wrong
the status linenothing, ever. That dollar figure at the bottom of your terminal
STEP 03/goal4 min

Give Claude the finish line, not the steps.

A prompt says what to do. A goal says what must be true when Claude stops, and a second model checks it after every turn. If you cannot write that sentence, you have not decided what done means.

What you would normally type

“Add a CSV export button to the dashboard.” Do not type it. No end state, no check, nothing off limits. Claude says it works and nothing can disagree.

Do this instead: Shift+Tab into auto mode, then paste as one message

/goal The dashboard header has an "Export CSV" button that downloads beacon-sites.csv. The CSV text comes from a new file csv.js that exposes window.toCsv(stores): a header row id,name,region,fillRate, posStatus,netStatus,openTickets,daysOfSupply and one row per site, values equal to the data. A new test tests/csv.test.js (node:test, no browser) loads data.js and csv.js the way tests/data.test.js does, parses toCsv(window.STORES) as CSV and asserts all of that. Write the test first. Then write csv.js as a stub whose toCsv returns an empty string, run the test, and show me the assertion failing before you write the real export or touch index.html. Done means `node --test tests/*.test.js` reports 0 failing, `node scripts/lint.js` reports 0 warnings, and the qa agent reports no blocking findings, all three pasted in your final message each turn. Only index.html, csv.js and the new test file may change. Stop after 8 turns and report what still fails. Do not commit, branch, or push.
End statea button, a file, named columns, one row per site
The checktwo commands and QA, output pasted every turn
Off limitsthree files may change
Stopping pointeight turns

The shortcuts, and what catches each

  • Edit the test so it passes. Only three files may change; the diff shows a fourth.
  • Hard-code six rows. The test compares with the data, not a number.
  • Skip a failing test. The pasted count shows fewer tests.
  • Call a failure unrelated and stop. The Stop hook sends it back.

You should see

  • Claude starts with the test, not the button, and shows it failing before the export exists. If that red says “cannot find module”, the test crashed before checking anything; ask for the stub. If it is green on the first run, stop and ask why.
  • After each turn: not yet met and a reason. Ctrl+O shows it in full:
not yet met  csv.js exports the right header, but the final message
             describes the test run instead of pasting it.

/goal on its own shows the condition, turns and spend. Let it run; read step 4 while it works.

Good to know: the same review as a hook

Today the goal requires the QA review, so the evaluator sends Claude back until it has run. In the engineering team’s setup the review is a Stop hook instead: when Claude says it is done, the hook starts a separate run of the QA agent on the diff, once per diff, and a blocking finding goes back to Claude before it can stop. Same rule, enforced by a hook rather than by the goal. One line does it:

claude -p --agent qa "Review the current diff. Report blocking findings."

It is a separate billed run each time, and it takes about a minute, which is why it belongs at Stop and not on every edit. Not part of today’s flow.

Who decides in a hook

  • A script (command; http and mcp_tool are the same idea). Free, instant, same answer every time. Anything with a pass line. Both of ours.
  • One model call (prompt). Yes or no from a fast model. Reading jobs: “did the message paste the output or describe it?”
  • A small agent (agent, experimental). Looks before answering. Only when a check needs evidence: “is there a test for every branch in this diff?”

Start with scripts. A model judge costs per event and can be talked into a yes.

STEP 05skillsubagentagent team6 min

Same check, three places to run it.

A skill runs in your session. A subagent runs in its own context and hands back a verdict. A team gives the test and the code different owners.

5a · skill · 1 min

A checklist, run by you

/pr-ready

What an engineer checks before a PR: tests, coverage, lint, only the allowed files changed, a PR description with the evidence pasted. READY or NOT READY. It is Claude grading its own work. It will flag CLAUDE.md in the diff: that is your step 4 edit, expected.

5b · subagent · 2 min

QA: the cases nobody wrote a test for

Use the qa agent on the CSV export: finance will open it in Excel.

Fresh context, read-only tools, never saw the conversation. It reads the tests to learn what is already proven, then does what they cannot: opens the file the way finance will, tries a quote in a name, a decimal, an empty fleet, the middle dot in a region, and compares with the live API. What comes back is findings: repro, expected versus actual, and the test that would have caught it. In rehearsal it found the one thing six green tests missed: no UTF-8 byte-order mark, so Excel shows the em dash and middle dot as garbage in every row. The goal in step 3 requires no blocking findings, so Claude fixes it and QA runs again.

5c · agent team · 3 min

The test and the code have different owners

Finance wants one more column, and this one is trivial on purpose: a currency column that says USD on every row. Two roles any team has: the tester (haiku) owns the tests and writes the failing assertion first; the builder (sonnet) owns the app code and changes one line. They message each other, not you. Make sure you are in auto mode first (Shift+Tab), because teammates inherit your permission mode and will stop to ask otherwise.

Want the two teammates in split panes? Set "teammateMode": "tmux" in .claude/settings.json, then start Claude inside a fresh tmux session. If an old one is around, clear it first (this closes every tmux session on the machine):

tmux kill-server
tmux new -s beacon
claude
Spawn two teammates: one using the tester agent type, one using the builder agent type. Finance wants a ninth column in the CSV export, currency, with the value USD on every row. The tester writes the failing test first and sends the assertion straight to the builder; the builder changes csv.js and replies. Do not ask me anything; report when green. Only csv.js and tests/csv.test.js may change.

Watch for the first message between them: a red assertion, not a plan. One round trip, under two minutes. Then git diff --stat should show exactly two files.

STEP 06PR/loopreviewsworktree8 min

Open the PR. Use the wait. Start the next ticket.

A real pull request. CI runs the suite on a clean machine, which takes minutes. A red check goes to Claude, not to you, and you use the wait.

1 · Open the PR, then let a loop watch CI

node scripts/open_pr.js
/loop 2m run: gh pr view --json number,headRefName and then: gh pr checks --json name,bucket Paste both outputs. Stop and tell me if headRefName does not start with agent/ or the number differs from the last round. A check is green only when its bucket is pass. Pending means wait for the next round. Do not use any other source. If a bucket is fail: read the log with gh run view --log-failed, fix the cause (in .github/workflows if the job broke before the tests ran, otherwise in the code), run node --test tests/*.test.js, push, and tell me what you changed. When every bucket is pass, report it and stop.

Every two minutes it checks. Red: Claude fixes and pushes. Green: stop it with this (Esc does not). The prompt makes Claude print which PR it is reading and paste the raw check list, so a switched branch or a stale memory cannot turn a red run green.

cancel the CI loop

/code-review high
/plugin install claude-security@claude-plugins-official

The loop is pushing here. Terminal C, and Claude Code makes the separate checkout:

Change the dashboard title in index.html to "Beacon · Site Health · Q3". Do not commit.

Own folder under .claude/worktrees/, own branch, same hooks. Or, in any session, say “work on this in a worktree”.

4 · See all of it

What you take home.
